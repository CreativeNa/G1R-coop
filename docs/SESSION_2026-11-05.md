# Session 2026-11-05 — what was done, what worked, what did not

A single report for whoever continues. Everything below was measured on the live game (build 1.2,
exe 175124992), two copies on one machine, except where it says otherwise.

Commits: `7101f16`, `71a399c`, `8b53ffd`, `a9f3758`, `67c02dd` (private repo).
Journal with the reasoning behind each step: `AI_HANDOFF.txt` (Russian), entries #20–#34.

---

## 1. Fixed: the UI died after a save load

**Symptom:** after F9 or loading from the pause menu, on either copy: no Esc, no inventory, no
quick-slot icons, `<MISSING STRING TABLE ENTRY>`, a spell-like crosshair, sometimes a transparent
save-selection window. Only a game restart helped.

**Cause (found by bisection, not by guessing):** the load synchronisation applied the load **twice**
on the receiving copy. The sender retransmits the event until it is acknowledged; a load resets the
module, the acknowledgement is lost, and the retransmission arrives ~30 s later and was applied
again. A double load kills the UI and the input state.

**Fix:** the applied event id is written to `native/build/last_load_lid.txt` as `pid:lid`; a repeat
with the same id for the same process is ignored. The file survives `mod_init`, which the core calls
again on every world load (`M module initialised` in the log) — that reset was why earlier attempts
failed: an in-memory list is wiped exactly when the repeat arrives, and a time window either missed
the repeat (8 s) or blocked legitimate presses (120 s).

Also: the saved-games page created to start the load is now deactivated **and removed** immediately
after `StartLoadingSave` (it kept the keyboard and drew as a transparent window), the cleanup
timeout went 60 s → 10 s, and the equipment module stays quiet for 5 s after a world change (the
caught `K2_AttachToComponent` access violations during teardown are gone).

**Verified:** 4 F9 presses → 4 loads, 2 delayed repeats caught, 0 AV, both copies at the same save
position. Full write-up: `docs/BUG_UI_AFTER_LOAD.md`.

## 2. Fixed: NPC health (found by the new tooling)

* the attribute-set cache was capped at 600 entries while the world has thousands, so most NPCs
  reported "unknown" and their health was never mirrored — cap raised to 8192;
* health was sent as one byte (clamped at 254) while people have 320 and a Templar 444 — the field
  is `uint16_t` now.

Verified by `tools\scenarios.ps1 -Only npc_health` (owner 270 → mirror 270) and by parity.

## 3. Added: recon mode — the mod now survives game patches

On an unknown exe size the core no longer refuses to start. It finds, by itself:

| Thing | How | Result on 1.2 |
|---|---|---|
| FNamePool block table | block 0 begins with the entry `"None"` | `0x9DFFD90` ✓ |
| FUObjectArray | scans writable sections for the `FChunkedFixedUObjectArray` layout, validates that the first 40 items know their own index | `0x9EB6BC0` ✓ |
| ProcessEvent | vtable slot 77 of the first UObject | `0x13A6B40` ✓ |

All three match the hand-made profile exactly. The result goes to `native/build/learned_profile.txt`,
so the next start does no scanning at all; the log also prints a ready-to-paste `BUILDS[]` line.
Self-test without waiting for a patch: `native/build/force_recon.txt`.
Details: `docs/RECON_MODE.md`. The core now also logs its build stamp (`built Nov 5 2026 ...`).

## 5. Performance: two real slowdowns found and fixed

| Module | Before | After |
|---|---|---|
| story | 3.3 ms/frame | **~1.0 ms** |
| pose | 1.6 | 1.6 |
| npc | 1.2 | 1.1 |
| menu+probe+anim+equip | 0.2 | 0.2 |
| **total** | **~6.3 ms** | **~3.9 ms** |

* the item scan checked its time budget only every 128 objects and overshot 1 ms → 3–4 ms; it now
  checks every 16 and uses 0.5 ms;
* the dialogue-widget rescan (a full object walk) ran every 3 s even when the widget was known — now
  15 s when cached;
* earlier the same class of bug caused real freezes: `find_object` walks the whole object array and
  was called 4×/s for the subtitles, which pushed `story` to 13–17 ms/frame. Object lookups are
  cached now.

The remaining spikes in the log (50–100 ms) coincide with the game's own worst frames (~100 ms at
30 fps), so they are not ours.

## 6. Verified working: ore pickup synchronisation

Reported as broken; tested live in the mine. The host took `BP_ItMi_Orenugget_World_C_2147365576`,
the guest logged `S item ... the other player picked it up` and destroyed its actor; then the guest
took one and the host did the same. World nugget counts stayed equal (30 → 29 on both). The item path
works because the nugget class has `m_PersistentId` + `m_WorldItemDefinition`.

Both "desyncs" that appeared during the test were transients: a chest set differed for ~30 s while a
cell streamed in (17/18 → 19/19), and a picked-up actor stayed in the picker's object array until the
garbage collector freed it (27/28 → 27/27). `parity` now treats a chest-set difference as a note and
only fails on the contents of chests both copies know.

## 7. Dialogues: the line reaches the guest, the display does not (PARTIAL)

This is the one thing that is **not finished**. State of the art:

**Works:**
* the host's line is read from `W_ConversationMain_C → RichTextBlock_DialogueLine → Text` (FText,
  converted with `KismetTextLibrary::Conv_TextToString`), including the game's markup
  (`"<h1>Дрейк</> Там, где досок нет..."`); several instances of the widget can be alive at once, so
  all of them are checked and the one with text wins;
* the text is sent in the story blob (a `[len16][text ≤600]` block appended after the cutscene
  block, sent also when only the line changed);
* the guest writes it into a subtitle widget and the FText really lands there (verified with
  `probe members`);
* the measured delay between the host's line and the guest's write is **66 ms average** (max 250);
* **one verified success**: at 20:39 the Drake line was visibly on the guest's screen (screenshot),
  using create → `AddToViewport` → `SetText(name, text)` on `W_SimpleSubtitlesGothic_C`.

**Does not work now:** the guest shows the game's own ambient line (Diego) instead of ours. The game
creates `W_SimpleSubtitlesGothic_C` instances for ambient conversations and writes into the same
class, so it wins.

**Tried and failed (do not repeat):**
* `ConversationWidget::ShowVoiceline` — never called by the game;
* `CinematicMainWidget::BP_OnVoiceline` — a Blueprint event, no native body, cannot be hooked;
* `UpdateText(ConversationVoicelineData&)` on the widget — returns 0;
* writing the `RichTextBlock.Text` property directly — writes fine, draws nothing;
* `SetAnchorsInViewport` / `SetAlignmentInViewport` / `SetPositionInViewport` — the first two broke
  `SetText`; the canvas slot is null for a widget added with `AddToViewport`;
* `Visibility` 0 and 4 — no difference;
* creating `W_SimpleGothicText_C` or `W_PlayerSpeak_C` instead — `WidgetBlueprintLibrary::Create`
  returns null (their constructors need data; also verified that Create returns null without a valid
  `OwningPlayer`);
* re-writing our text every frame to outrun the game — the ambient line still wins;
* `SetText` on the created widget occasionally throws a **caught**
  `EXCEPTION 0xc0000005 in ProcessEvent(SetText)` inside the engine.

**Next idea (not tried):** do not draw anything; let the game show the line itself with
`AbilityTask_SayVoiceline::TaskSayVoiceline(OwningAbility, Text, SoundKind)` — the native path the
game uses for subtitles. It needs a valid `OwningAbility` of the speaking NPC, which is the real work.
Voice stays host-only in any case: the audio plays in that process and cannot be sent to another.

**Honest note on the one success:** it was not committed when it worked, then the source file was
damaged twice by careless patch scripts and restored from git, which brought back a later version.
Reconstructing the same code afterwards did not reproduce the result, so the success also depended on
the game's state at that moment (no ambient line playing).

## 8. Mistakes worth remembering

1. **Commit the moment something works.** The only verified subtitle success was lost because it
   existed only in the working tree.
2. **Never locate code by a bare function name.** `s.index('static void subs_apply(CoreAPI *a, const char *txt)')`
   matched the *forward declaration* at the top of the file and cut ~1000 lines out. Twice. Use an
   anchor that includes the body (`... \n{`) or `rindex`.
3. **Any per-tick engine lookup is expensive.** `find_object` walks the entire object array; cache it.
   That single mistake caused 13–17 ms/frame and the freezes the user felt.
4. **Compare across copies, never the same field on both**, and give world-actor comparisons time:
   streaming and the garbage collector make 30-second differences that look like bugs.
5. **A long time window for duplicates is as bad as none.** The right key is the event id, not time.

## 9. Still open

* **journal / glossary entries are not synchronised** (found in live play): after a conversation the
  entry appears only for the host, because the unlock lives in Document::RememberSegmentUnlocked /
  DocumentSubsystem::NotifyPotentialSegmentUnlock - and those are AngelScript bytecode, so they
  cannot be hooked. The fix path (poll FindSegmentsUnlockedByReader, replay RememberSegmentUnlocked
  on the other copy) is written down in docs/BUGS.md;
* dialogue subtitles (above) — and the voice, which is out of reach by design;
* chest lid not drawn on the other copy (visual only);
* rare caught access violation in `story` `send_blob` (a few per hour, does not stop the game);
* two-PC test over Radmin;
* pose is now the most expensive of our modules (1.6 ms/frame, one engine call per bone); the
  adaptive stride threshold could go 1.8 → 1.0 ms for ~0.8 ms, at some cost in smoothness.

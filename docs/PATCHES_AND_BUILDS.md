# Game builds: what is known (PRIVATE notes, do not publish)

Everything here comes from our own analysis of a running copy of the game we own. It contains exe-specific addresses and recon results, which is the kind of content the G1R Modkit licence calls reverse engineering: keep this file in the private repository only.

## Old build (before 1.1)
- Steam build id `24169431`, `G1R-Win64-Shipping.exe` size **171704320** bytes (file date 29.10.2026 21:59).
- Addresses (RVA from the exe base), found earlier with UE4SS signature scans:
  - `GUObjectArray` 0x9B9D440 (the `FChunkedFixedUObjectArray` inside it starts at +0x10: `Objects**`, `PreAllocated*`, `MaxElements`, `NumElements`, `MaxChunks`, `NumChunks`; 24-byte `FUObjectItem`, 65536 items per chunk)
  - `FName::ToString` 0x11CE2A0, `FName::FName(const TCHAR*, EFindName)` 0x11AFA80
  - `UObject::ProcessEvent` 0x13A2920
  - `GameEngine` tick: the vtable slot 95 of the `GameEngine` instance (scan address 0x379AD70)
  - audio predicate crash guard at exe+0x5BE3970 (a geometry predicate called from the audio code read a null `View`: a stub in executable memory within +-2 GB, patched with an atomic 8-byte write; see `native/n2.inc`)
- Object layout (UE 5.4): `UObject` index +0xC, `ClassPrivate` +0x10, `NamePrivate` +0x18 (`ComparisonIndex` int32, `Number` int32), `OuterPrivate` +0x20; native function pointer of a `UFunction` at +0xD8 (used to observe calls).

## Build 1.1 (Steam build id `26295476`, installed 04.11.2026)
- `G1R-Win64-Shipping.exe` size **175029760** bytes (SizeOfImage 179318784). Every old RVA is invalid.
- Found with the recon DLLs `native/scan_gc.c` and `native/scan_names.c` (they only read memory):
  - `GUObjectArray` **0x9E9FBC0**, same layout as before (`Objects**` at +0x10), about 197 thousand objects in the main menu
  - `FNamePool`: block table at **0x9DE8D90** (the pool struct starts at 0x9DE8D88: lock, `CurrentBlock`, `CurrentByteCursor`, then `Blocks[]`); an entry is `uint16 header (len = header >> 6, bit 0 = wide)` + characters, stride 2, 65536 entries per block (0x20000 bytes); the first entry is "None"; `FName` index = block << 16 | offset / 2. Names are read directly, so `FName::ToString` and the constructor are not needed (the core has own replacements: `pool_str`, `fname_make`)
  - `UObject::ProcessEvent` = vtable slot **77** of any `UObject`, **0x13A6AD0** (prologue `40 55 56 57 41 54 41 55 41 56 41 57 48 81 EC 70`); the `UObject` vtable is at 0x77FCEF8
  - object layout unchanged (checked on the first objects: "Object (class Class)", "Actor (class Class)", ...)
- Not found / not verified on 1.1: the `GameEngine` tick slot (the core uses vtable slot 95), the audio crash guard (the core only patches when the expected bytes are there), whether the injection check reacts later (tested only in the main menu).
- The core (`native/coopdll.c`) now has build profiles (`BUILDS[]`, picked by the exe size) and a name pool reader; first test of `coopdll_64.dll` on 1.1 was interrupted (the previous run had an old DLL loaded in the same process: always test in a fresh process).

## Anti-injection in 1.1
- Window text: "Potentially malicious code injection found, game will exit now. If you want to mod the game please use the provided API." It named `...\G1R\Binaries\Win64\UE4SS.dll` (with `dwmapi.dll` and `UE4SS-settings.ini` next to the exe). After those files were moved away, the game started normally.
- Our own DLLs (`coopdll_63`, `scan_gc`, `scan_names`) injected into a clean 1.1 in the main menu did NOT close the game (a few minutes observed).
- `inject.exe` is flagged by Windows Defender as unwanted software (quarantined once, restored by the user).

## Official route (G1R Modkit)
- Mods go to `G1R/Mods/<Name>/` (`GothicMod.json`, `Script/*.as`, `Config/*.ini`); the in-game tools (`-ingametools`) give ImGui panels (`UIngameTool`) and an actor outliner.
- The shipped main story game mode derives from `AG1RGameModeCooperative` (`AMultiplayerGameMode`): the menu game mode reports max players 16 and a lobby map. The scripts ship `UPlayerConfigTwo_G1R` .. `Five`. Our spike mod (`mod/G1RCoop`) adds the second player config.
- Networking from script crashes the game in the shipped build: `CreateSession(true|false)` (null read 0x1d8), `open ?listen` and `open 127.0.0.1` (null read 0x80); `FindSessions` does nothing visible.
- Script details learned: `PlayerController::ConsoleCommand` is not available from script (use `System::ExecuteConsoleCommand(cmd, pc)`); a mod class with `UCLASS(meta=(ReplaceParentClass))` replaces the base class; `Print()` shows nothing on screen; the saving block uses the gameplay tag `State_NormalSaveBlocked` (sleeper dreams, puzzles, crafting places).

## Chest sync status (1.1, two copies)
- Works: "in use" lock (the friend cannot open a chest the other player holds). Call parameter names are case-sensitive (`Value`, `SectionName`, `AnimMontage`); lower-case names silently give zero values.
- Event chain for the lid works end to end (host observes `Multicast_JumpSectionInteractMontage` / `Multicast_StopInteractMontage` on the chest actor, the guest replays them, mesh position moves 0..10 s), but the lid is NOT visibly drawn on the other copy. `TickAnimation`/`RefreshBoneTransforms` are not callable UFunctions. Open idea: the rendered lid may be a different component/instance than m_SkeletalMeshComponent.
- Items put INTO a chest (verified in the real game, 2 copies): the giver's DataModule gets `Server_MoveItemFromActorToOtherActor(Actor=hero, OtherActor=chest, ItemPos=id, ..., justConsume=1)`; the entry is already gone when it is seen, so the hero's inventory (`GetItemsIn`, stride 184: +0 item id, +8 definition class ptr) is cached while near a chest. The other copy calls `Server_AddNewItem(type 1, definition class found by name, amount, zero payload)` on the chest module. The item count of a chest does not change when the item joins an existing stack.
- A save may hold a stale "in use" flag on a chest: it is cleared when the chest is first tracked, and "in use" only counts near the chest (lock heartbeat 4 s, released after 15 s of silence).

## Open bug: white veil / `<MISSING STRING TABLE ENTRY>` after a load (1.1, two copies)
Seen: a grey-white full-screen overlay with the text `<MISSING STRING TABLE ENTRY>` in the top-left corner (looks like a loading-screen layer that is not cleared), on one or both copies right after loading a save; usually goes away after a while or after the next load; it once stayed on the guest. It also appeared before save-load sync existed.

Suspects, in order of likelihood:
1. The test "lite" launch settings (`-ExecCmds`: `r.Streaming.PoolSize 200`, `r.MipMapLODBias 3`, `r.Streaming.MaxTempMemoryAllowed 32`, `r.ScreenPercentage 30`, `perf_cmds.txt`): too small a texture pool starves the UI/loading-screen textures and string tables. Test: run both copies with `start_coop_11.ps1 -Full` (RAM permitting), or only drop `MipMapLODBias` and raise the pool.
2. Repeated access violations in `ProcessEvent(K2_AttachToComponent)` (exe+0x363628e, caught by the core) on every load/F9: the equip/npc modules attach weapons while the world is being replaced. A fault inside the loading sequence can leave `LoadingScreenHelperSubsystem` / HUD fade state half-done. Fix idea: do no module work (equipment attach, NPC mirrors, chest polling) while the hero/world is being replaced (detect "hero changed" and idle for ~5 s), and validate actors before `K2_AttachToComponent`.
3. Save-load sync itself: the guest load is started by calling `SavedGamesPageWidget::StartLoadingSave` (or a posted F9) while the guest may be in a state where the loading widgets are not ready. Test: load the same save on the guest by hand and see whether the veil still appears; compare with a plain single-copy load.
4. Something else in the loading flow: observers on `StartLoadingSave`/`AsyncLoadGameFromSlot` replaced native bodies (they only record and call the original, so unlikely).

Plan: (a) log the veil: record `LoadingScreenHelperSubsystem` state and the open widgets (`findall` on HUD/Loading classes) while it is on screen with `dev.ps1 probe`; (b) try the three tests above one at a time, change one thing per run; (c) add the "idle during world change" guard to the modules; (d) if the text is a localization table problem, find which string-table asset is missing (log `FText`/string-table names near the overlay).
Also seen once: an empty loot window with "Label" placeholders (fixed by releasing the mirror once it is dead).
- Veil bug clue (user): swinging the pickaxe a few times clears the veil completely (so it is a state of the hero/camera/HUD that combat or weapon-ready clears, not a texture problem).
- Snapshot taken with the veil visible on one copy: Ultra Dynamic Sky and Weather values (Fog 1, cloud coverage 0.9, base fog density) are identical on both copies, so it is not the weather/fog. Still to compare between a veil copy and a clean one: the 11 `PostProcessVolume` actors (enabled, blend weight, exposure), camera manager (ViewTarget blend, fade), the hero's weapon-ready state, `GothicHUD` visibility; take both snapshots at the same moment, then swing the pickaxe and take a third.
- VEIL CAUSE FOUND (1.1): with the veil `GothicCameraManager::m_CurrentBehaviour` (byte @ +10168 in PlayerCameraManagerBP_C) is 2; in the normal state it is 16 (the pickaxe swing makes the game set it back). Diff of ~270 hero/camera/HUD/controller properties between a veil and a clean state showed nothing else. Post-process volumes, sky, weather: identical. Fix idea: after a load (and while the veil state persists) write 16 into m_CurrentBehaviour of the camera manager; `dev.ps1 probe "@<seat> set <ptr> m_CurrentBehaviour 16"` tested by hand on the veil copy (result noted below). Tool: tools/veil_snapshot.ps1.
- Veil, round 2 (host, same copy before/after a pickaxe swing, 627 properties of hero, its components, camera manager, controller, HUD, player state): the ONLY non-positional differences are `GothicCameraManager::m_CurrentBehaviour` 2 -> 16 and the camera view data (`ViewTarget`, `CameraCachePrivate`, `LastFrameCameraCachePrivate`, 2 KB structs that hold the camera's point of view and post-process settings; the probe prints only their first bytes). Writing 16 into the byte, or calling `GothicCameraManager::RefreshCameraConfig`, does NOT remove the veil (the game sets the byte back to 2), so the byte is a symptom. The cause lives in the camera point-of-view / post-process data or in a state the swing (combat-ready camera) rebuilds.
- Next ideas: (1) let the probe print whole struct values and diff the 2064-byte `CameraCachePrivate` (look for PostProcessBlendWeight / PostProcessSettings fields, FOV); (2) find the game function that enters the weapon-ready/combat camera state (draw weapon) and call it once after a load, then holster; (3) check `PlayerCameraManager` view-target blend and `bUseClientSideCameraUpdates`.

## Saves can carry the broken state (found 2026-11-04), and dialogue status
- The "UI dead after a load" bug (no Esc, no inventory, no notifications, veil) was in the SAVE FILES, not in the code: both copies on one PC share one SaveGames folder, and slots written by a session that had applied the host's quest states by raw byte writes (bypassing `QuestSubsystem`) kept that state, so every later F9/Continue reproduced it. Rule: write nothing raw into game state that gets saved (health maximum, quest states); keep clean save backups.

## Dropped items sync: skeleton, partly working (2026-11-04)
How: a drop shows as `Server_ConsumeItem` on the hero's own inventory module; for 10 s afterwards the item scan runs faster and a newly tracked world item with no persistent id within 8 m is sent (event type 14: `<name without BP_ and _World_C>|<drop flag>|x/5|y/5|z/5`; drop variants are `BP_<name>_World_Drop_C`); the other copy loads the world class through `ItemDefinition::LoadAndGetThrowVisualWorldClass`/`LoadAndGetVisualWorldClass` on `Default__<name>` when it is not loaded, spawns the actor (`spawn_actor` + `K2_SetActorLocation`) unless the same class lies within 150 units, and tracks it under the same key (class + position in 25-unit cells computed from the position rounded to 5 units on both sides, `drop_key`). Entries spawned for the friend carry `used = 77` (a vanishing is not announced as a pickup). A pickup observed in `Server_PickWorldItem` of an item that is already tracked is announced under its own key.
Verified once by the user: drop on the host -> appears on the guest; pickup on the guest -> gone on the host; pickup by the host of an item dropped by the guest -> gone on the guest.

## Dropped items and stacks: works roughly (user, 2026-11-04), skeleton, needs repeats
Final design: a drop is detected as `Server_ConsumeItem` on the hero's own inventory module + the item scan sped up for 10 s (a new id-less world item within 8 m). Event type 14 carries the real item name, a flag (0 world class, 1 `_World_Drop_C` pile, 2..4 stack from `GroupGeneric/GroupArrow/GroupBolt`) and for stacks the amount from the group actor's `m_ItemCount`; the other copy loads the pile class (through `ItemDefinition::LoadAndGetThrowVisualWorldClass`), spawns ONE pile, tracks it under the same key (`drop_key`, entry `used = 77`, `fname` must be set or `check_items` drops it as "dead", `base` = stack amount) and un-removes the key (an earlier pickup at the same spot must not delete the new item). On a pickup of such a pile the game gives 1 item; 1.5 s later the rest (N-1) is added with `Multicast_AddNewItem` (inventory type 0 in the call); `Server_AddNewItem` alone does nothing for the hero's bag, so the old give-aid only worked through its multicast fallback. Bag amounts are logged (`S count:`). Stacks above 99 would need several entries.
Findings along the way: `LoadAndGet...VisualWorldClass` loads an unloaded world class; the plain `BP_<item>_World_C` of berries is the whole bush, the drop pile is `_World_Drop_C`; group actor pickup ignores the amounts we write into `m_ItemCount`/`m_ReplicatedWorldData`; `find_object(NULL, ...)` does not find blueprint classes unless loaded; a full-object snapshot every 2.5 s caused severe lag (never scan all objects regularly).
Known cosmetic: the pickup shows "+1" first and then "+N" (two notifications). To repeat: drop and pick up in both directions, stacks of 2/10/50/99, other items (arrows, coins), stack above 99, drop in the same spot repeatedly, drop while the friend is far away.

### NPC sync: runtime-named NPCs were "missing" on the guest (2026-11-04)
Cause: NPCs are matched by a hash of the object name; spawner-made ones end in _<instance number> (e.g. Character_Molerat-WP_AM_MOLERAT_SPAWN_01-3_2147342717) that differs between the copies, so the guest found no actor (log: mirroring 2, missing 2). Fix: the trailing _<6+ digits> is cut before hashing (npc_module.c rescan_slice); new logs "N host reports ..." and "N guest: no actor for ...". After the fix the stats read mirroring 6, missing 0. Not yet confirmed visually in a fight; if two actors share one base name they would collide.
NPC name-hash fix, first live test (user report): a group of enemies was in sync on both copies, three killed, all died without bugs, all lootable on both. Logs: missing 0, no access violations. Once only: repeat in other places. Note: host reports "bone-driven here 3" but the guest shows "bone-driven mirrors applied 0" (bone pose copy not applied on the guest; effect not seen).

### NPC in a dialogue "walks / turns on the spot" on the guest (2026-11-04)
Cause: the guest keeps the mirror NPC controller possessed (unpossess crashed the game), so its local AI kept trying to walk and to turn toward its own target while the host-driven position/yaw was forced back every frame. Fix (npc_module.c): while the owner stands (speed < 5) the mirror CharacterMovement tick is off and StopMovementImmediately / Controller::StopMovement are called; the controller control rotation is set to the owner yaw every frame. Result (user report, Drax and a second NPC): the NPC stands calmly. Probably solved, tested on two NPCs only. Also seen: the guest shows human clips about 1.5 s late (not investigated).
